# ADR 008: Initial registration reserves the Subscription and creates a pending ledger row BEFORE charging Stripe

**Status:** Built — 2026-08-28 (PR 2 of `docs/plans/billing-anchor-and-sibling-discount-plan.md`, alongside ADR 005), pending owner local testing + commit.

## Context

Tightening Guard A to "one active subscription per student, any schedule" ([ADR 005](./005-one-active-subscription-per-student.md)) exposed a race the old, narrower guard structurally couldn't hit: `registration.service.js`'s `create()` charges Stripe *before* creating the `Subscription` document (`docs/plans/registration-ledger-plan.md` D3 — "charge-first ordering is KEPT," chosen so a declined card leaves nothing persisted). That design's safety argument for a race ("both racers share ONE real charge" via a shared Stripe idempotency key) only holds when the race is over the *same* schedule. Once Guard A blocks a second active subscription regardless of schedule, two near-simultaneous registration requests for the same student on two *different* schedules each carry a different idempotency key — both charges can succeed for real, and only one request can win the `Subscription.create()` call. The loser has a real, successful charge with no `Subscription`/`Registration` row to show for it: money taken, nothing delivered, no record explaining why.

Three narrower fixes were considered and rejected (see Alternatives). Researching CKQ's own initial-enrollment flow (`chesskqwebsite/backend/backend-2.0/src/services/registration.service.js`'s `groupClassRegistration()`) surfaced that CKQ already solves this differently: it creates its Subscription and Registration documents **before** calling Stripe, and a failed *initial* charge is **not** rejected outright — it enters the exact same retry/dunning cron used for renewal failures (3 attempts, daily, cancel on exhaustion). Frisco's own renewal path already has the identical machinery (`renewal.service.js`'s create-pending-first sequencing, `docs/plans/registration-ledger-plan.md` D4/D6) — this ADR adopts CKQ's shape for the *sequencing and dunning* decision while reusing Frisco's own already-built, already-tested code for the *mechanism*, rather than porting CKQ's code.

## Decision

**`create()` reserves the `Subscription` row and a `pending` ledger row before ever calling Stripe, and a failed first charge enters the same retry/dunning cycle a failed renewal already goes through.**

1. **Reserve first.** After all validation and charge/discount/proration computation (all pure, no writes) but before any Stripe call: create the `Subscription` (`status: 'active'`) with its period fields already computed (`currentPeriodStart`/`currentPeriodEnd`/`nextBillingDate` — these don't depend on whether the charge succeeds, only on the anchor date and proration math already computed). Guard A's unique index fires here, atomically, for *any* schedule combination — a racing duplicate request never reaches Stripe at all. This is a genuine hard block, not a cleanup-after-the-fact mitigation.
2. **Then create the ledger row**, `status: 'pending'`, `eventType: 'initial'` — the same shape `renewOne()` already creates for a renewal's pending row.
3. **Charge via shared logic, not duplicated logic.** `renewal.service.js`'s `chargeLedgerRow()` / `finalizeSuccessfulCharge()` / `finalizeFailedCharge()` (and the email senders they call) move into a new shared module (`backend/src/services/billing/chargeFinalization.service.js` or similar — exact name at builder's discretion) that both `registration.service.js` and `renewal.service.js` import. `registration.service.js` no longer hand-rolls its own `stripe.paymentIntents.create()` call or its own success/failure branching — it calls the same finalization functions renewals use, with `attemptNumber: 1`.
4. **Success** → `finalizeSuccessfulCharge()` marks the row `completed`, sets the period (the existing `advanceSubscriptionPeriod()` — a `$set`, not an increment — works unchanged whether this is the first period or the Nth), and *only now* does `create()` grant roster/session access (`addStudentToRoster`) and send the confirmation email. Access is never granted before a successful charge — owner-decided explicitly, matching today's behavior.
5. **Failure** → `finalizeFailedCharge()` sets `retryCount`/`nextRetryAt` exactly as it already does for a renewal failure. The existing `runRetries()`/`retryOne()`/`cancelAfterExhaustion()` machinery (registration-ledger plan D6, `MAX_PAYMENT_RETRIES = 3`) picks it up daily with **no changes** — a brand-new signup's failed first charge is, from the retry cron's point of view, indistinguishable from a renewal's failed charge. On exhaustion, `cancelAfterExhaustion` cancels the never-successfully-paid subscription; roster access was never granted, so there's nothing to remove beyond what that function already does defensively.
6. **API contract change.** `POST /registrations` still returns `201` when the registration is *accepted* (the reservation succeeded), but the response body's `paymentIntentStatus`/status field distinguishes `completed` from `pending`/`failed_retrying` — a 201 no longer means "your card was charged" unconditionally. The parent-facing register flow must show a distinct "we're processing your payment" or "your card was declined, we'll retry over the next few days" state instead of an unconditional success screen. This is a real, scoped frontend change, not just a backend one.

## Consequences

- The cross-schedule race is closed at the DB layer, with zero orphaned charges possible and no refund logic needed — consistent with ADR 001/006's standing "no refund logic" position, now achieved structurally rather than by exception-handling.
- Frisco's initial-registration failure behavior now matches CKQ's and the owner's stated expectation ("current flow is when someone registers we have 3 retries before we actually cancel their subscription") — previously true only for renewals, not for a brand-new signup's first charge.
- One implementation reduction, not an addition: `registration.service.js` stops duplicating Stripe-charging/finalization logic that `renewal.service.js` already has built, tested, and hardened (idempotency keys, `StripeCardError` vs. non-succeeded-status handling, fire-and-forget email contract). Extracting it to a shared module means a future bug fix in charge finalization is written once, not twice.
- A subscription can now exist in the DB in a state that never had a successful charge (mid-dunning on its very first attempt) — `lastChargeAmount: null` remains the correct signal for "never successfully charged," distinct from a renewal's dunning (where `lastChargeAmount` reflects the last *successful* period). No new field is needed to distinguish the two; this falls out of fields the schema already has.
- The Stripe idempotency key for the initial charge moves from `initial-registration-${studentId}-${scheduleId}-${date}` to being keyed on the ledger row's own `_id` (`payment_${row._id}`), matching `chargeLedgerRow()`'s existing convention — this is *stronger*, not weaker, since the row's `_id` is stable and unique the moment it's created, before any charge is attempted.
- Frontend: the register-flow's success state must branch on the new status field. A `pending`/`failed_retrying` result is not an error the wizard should treat as a failed submission — the registration was accepted; only the payment is still resolving.

## Alternatives considered

- **Auto-refund the loser's charge in the `catch` block** — rejected; this project has deliberately avoided introducing any refund-issuing code (ADR 001, ADR 006), and it only cleans up after the race rather than preventing it.
- **Scope the Stripe idempotency key to student+date only (drop scheduleId)** — rejected; a legitimate same-day cancel-then-re-register-for-a-different-schedule would collide with a stale key from an unrelated, already-completed transaction earlier that day, since Stripe retains idempotency keys for 24 hours. Would trade a rare race for a real, more frequent breakage.
- **Leave the race window undocumented/accepted as a rare edge case** — rejected by owner: "we should have a hard block on that as well."
- **Keep charge-first, just check-then-reserve a lightweight lock document instead of the real `Subscription`** — rejected as needless indirection; the `Subscription` document *is* the natural reservation once its period fields can be computed up front, so a separate lock record would just be the same idea with an extra collection.
